# managed-document-updates Specification

## Purpose

Make generated instruction updates auditable and recoverable while preserving user-maintained files, detecting local edits, and removing only outputs demonstrably owned by the tool.

## Requirements

### Requirement: Managed outputs have durable ownership records

The CLI SHALL maintain versioned `.agents/agents-state.json` records for generated documents, including their canonical relative paths, prior generated hashes, source provenance, and generation identity. Ownership SHALL be independent of the content lock and SHALL NOT extend to unrelated files or arbitrary skills.

#### Scenario: A composition is successfully applied
- **WHEN** a synchronization commits new generated documents
- **THEN** durable ownership records identify their generated bytes and source provenance
- **AND** the records describe the same completed generation as the published lock and documents

#### Scenario: A directory contains unrelated Markdown
- **WHEN** a destination directory also contains a document not owned by the tool
- **THEN** that document is not added to the ownership records merely because of its location or generated-file notice

#### Scenario: A company authors its own content base
- **WHEN** base initialization or base validation runs in a content-only repository
- **THEN** its editable templates and conventions remain authored inputs without consumer ownership records
- **AND** a project consuming that base records ownership only for its own generated documents

### Requirement: Initial ownership requires proof of expected content

For a project without ownership records, the CLI SHALL adopt an existing generated target only when its bytes match the expected generation from the selected sources after the established newline normalization. A generated-file notice alone SHALL NOT authorize adoption, replacement, or removal. Ambiguous targets SHALL be reported as conflicts.

#### Scenario: Existing valid generated documents are adopted
- **WHEN** a project's pre-existing targets match a valid generation from its selected sources
- **THEN** a normal synchronization can record ownership without changing the rendered document contents
- **AND** a preview reports the metadata that would be introduced

#### Scenario: A pre-existing target differs from expected generation
- **WHEN** an existing target differs and there is no prior ownership record proving its last generated state
- **THEN** synchronization reports an ownership conflict and preserves the file
- **AND** the diagnostic directs the user to reconcile the source and published document before adoption

#### Scenario: Unselected files exist before ownership initialization
- **WHEN** a candidate project contains unrelated files outside its selected output set
- **THEN** those files remain unmanaged and unchanged
- **AND** no prior development catalog or generated banner creates ownership

### Requirement: Local edits are protected from implicit overwrite

Before replacing or removing an owned target, the CLI SHALL compare its current bytes with the recorded generated state. An unexpected edit SHALL block the entire application plan and identify the source-level reconciliation required. The CLI SHALL recheck expected file state immediately before applying its plan.

#### Scenario: A user edits a generated document directly
- **WHEN** the target differs from its recorded generated hash and the plan would replace or remove it
- **THEN** the CLI reports a conflict without applying any project changes
- **AND** it preserves the edited bytes

#### Scenario: A target changes after planning
- **WHEN** another process modifies a target between plan creation and application
- **THEN** application detects the changed precondition and aborts or rolls back the transaction
- **AND** does not overwrite the unrelated modification

### Requirement: Cleanup removes only proven stale outputs

When a manifest or family no longer selects a previously generated document, the CLI SHALL plan its removal only if ownership and unchanged generated bytes are established. Paths outside the active ownership set SHALL NOT be deleted by filename inference. Moving an output directory SHALL apply the same ownership rules to old destinations.

#### Scenario: A selected convention is removed
- **WHEN** a previously owned convention is removed from the composition and its output is unchanged
- **THEN** the plan includes its output as a removal
- **AND** successful application updates ownership without affecting unrelated documents

#### Scenario: An old flattened filename is unrelated
- **WHEN** a nested convention has a matching flattened basename elsewhere but the old file has no proven ownership
- **THEN** the CLI preserves the old file and reports any ambiguity that affects the requested generation

#### Scenario: A later selection removes an owned output
- **WHEN** an explicit valid future content update deselects an unchanged owned document
- **THEN** the shared plan removes that document and updates ownership
- **AND** files outside the ownership set remain preserved

### Requirement: Preview and check share the application plan

The CLI SHALL derive preview, check, and application from the same resolved inputs and validated desired outputs. Plans SHALL identify creates, updates, removals, adoptions, conflicts, and metadata changes. A second successful synchronization with unchanged inputs SHALL leave managed bytes and durable metadata unchanged.

#### Scenario: Preview precedes an unchanged application
- **WHEN** a consumer previews and then applies a composition whose inputs and preconditions have not changed
- **THEN** the application performs the changes described by the preview
- **AND** reports any invalidated precondition rather than silently applying a different composition

#### Scenario: Repeating a completed generation
- **WHEN** an unchanged consumer repeats synchronization and check
- **THEN** synchronization performs no managed-file or metadata rewrites
- **AND** check exits with code 0

### Requirement: Project mutations are recoverable transactions

Document, manifest, lock, and ownership changes in one operation SHALL be staged and journaled before replacement. Recoverable failures SHALL restore the previous state; an interrupted operation SHALL retain recovery evidence and block further normal mutation. Per-file replacement SHALL be atomic where supported without claiming instantaneous atomicity across multiple files.

#### Scenario: A later document write fails
- **WHEN** an application fails after replacing an earlier target
- **THEN** the CLI restores recorded pre-operation bytes and durable metadata when recovery preconditions hold
- **AND** reports failure instead of declaring the generation complete

#### Scenario: The process exits during application
- **WHEN** an unfinished journal exists on the next invocation
- **THEN** normal mutation refuses to proceed and explains the pending transaction
- **AND** sync preview and validate diagnostics can report its status without repairing it implicitly

### Requirement: Recovery preserves edits made after interruption

For a pending journal, sync --dry-run SHALL report verified rollback actions. Sync SHALL obtain exclusive access and restore the prior state only if targets match recorded states, then stop before normal generation. Independent changes SHALL be preserved and reported as conflicts. No additional public recovery root SHALL be exposed.

#### Scenario: Rolling back an interrupted generation
- **WHEN** the recorded targets still match the interrupted transaction's known states
- **THEN** recovery restores the complete recorded prior state and clears the completed recovery record
- **AND** subsequent normal synchronization can run

#### Scenario: A document is edited after a crash
- **WHEN** recovery finds content matching neither the recorded previous nor proposed transaction state
- **THEN** recovery preserves that content and its backups, reports a conflict, and does not claim successful recovery

### Requirement: Concurrent mutations cannot share one project transaction

The CLI SHALL allow at most one mutating composition or recovery operation per canonical project root. A second mutation SHALL fail with a clear diagnostic. Stale-lock recovery SHALL verify ownership and pending transaction state before changing a lock; it SHALL NOT infer safety solely from a missing process identifier.

#### Scenario: Two synchronizations start together
- **WHEN** a consumer starts two mutating synchronizations for the same canonical root
- **THEN** only one can apply changes
- **AND** the other reports contention without modifying the active transaction

#### Scenario: A crashed process leaves a lock
- **WHEN** recovery encounters a lock from an interrupted invocation
- **THEN** it checks the recorded owner and journal before recovering under exclusive access
- **AND** preserves ambiguous ownership for user reconciliation
